# CareSignal Backend — คู่มือติดตั้ง (15 นาที)

ระบบหลังบ้านจริงบน **Supabase (PostgreSQL)** พร้อม Row Level Security 4 บทบาท,
ระบบยืนยันตัวตน, ความยินยอมแยกวัตถุประสงค์ และ audit log ที่แก้ไม่ได้

---

## ขั้นที่ 1 — สร้างโปรเจกต์ Supabase (5 นาที)

1. เปิด https://supabase.com → **Start your project** → สมัครด้วย GitHub
2. **New Project**
   - Name: `caresignal`
   - Database Password: ตั้งแล้ว**เก็บไว้ให้ดี** (ใช้ตอนกู้ระบบ)
   - Region: **Southeast Asia (Singapore)** — ใกล้ไทยที่สุดที่มีให้เลือก
3. รอ provision ~2 นาที

> **หมายเหตุเรื่อง data residency:** Supabase ไม่มี region ในไทย ข้อมูลจะอยู่สิงคโปร์
> สำหรับ pilot ถือว่ายอมรับได้ แต่ถ้าบริษัทประกันกำหนดให้ข้อมูลสุขภาพต้องอยู่ในไทย
> จะต้องย้ายไป self-host หรือผู้ให้บริการในไทยตอนขึ้น production จริง
> — **เป็นคำถามที่ควรถามฝ่ายไอทีของบริษัทประกันก่อนขยายผล**

## ขั้นที่ 2 — สร้างตารางและกฎความปลอดภัย (3 นาที)

เปิด **SQL Editor** ใน Supabase แล้วรันตามลำดับ:

1. `01_schema.sql` — ตาราง 6 ตัว + view สำหรับบริษัทประกัน
2. `02_rls.sql` — Row Level Security + trigger ความปลอดภัย

รันทีละไฟล์ ต้องขึ้น **Success** ทั้งสองครั้ง

จากนั้นรันไฟล์ที่เหลือ **เรียงตามหมายเลข** `04_` → `21_` ไฟล์ละครั้ง
แต่ละไฟล์เป็นส่วนเพิ่ม (ตาราง view ฟังก์ชัน หรือกฎสิทธิ์) และรันซ้ำได้โดยไม่เสียข้อมูล

> `21_insurer_trend.sql` สร้าง view `insurer_monthly` ที่แดชบอร์ดบริษัทประกัน
> ใช้วาดกราฟแนวโน้มรายเดือน ถ้ายังไม่รัน หน้าอื่นทำงานปกติ แต่การ์ดกราฟจะขึ้นว่า
> "ยังไม่มีข้อมูลย้อนหลังพอจะวาดกราฟ"
>
> `22_referral_forms.sql` (ล่าสุด) เพิ่มคอลัมน์ `assessments.detail` และเปลี่ยน
> `build_referral_package` ให้คืนชุดข้อมูลรุ่น 2 ที่แบบฟอร์มส่งต่อสหวิชาชีพใช้ พร้อม
> `return_review` รุ่นรับแบบฟอร์มของวิชาชีพ ถ้ายังไม่รัน ใบส่งต่อยังเปิดได้แต่ช่อง
> ประวัติล้ม/ท่าทรงตัว/บ้านจะว่าง และผู้เชี่ยวชาญส่งแบบฟอร์มไม่ได้ (ระบบจะแจ้ง error) 

## ขั้นที่ 3 — เชื่อมกับหน้าเว็บ (2 นาที)

ไปที่ **Project Settings → API** คัดลอก 2 ค่า แล้วใส่ใน `cs-backend.js`:

```js
var CS_CONFIG = {
  url:     "https://xxxxxxxx.supabase.co",
  anonKey: "eyJhbGciOi..."
};
```

> `anon key` ปลอดภัยที่จะอยู่ในโค้ดฝั่งหน้าเว็บ เพราะ **RLS เป็นตัวคุมสิทธิ์จริง**
> ไม่ใช่ตัว key — ห้ามใส่ `service_role key` ลงในหน้าเว็บเด็ดขาด

## ขั้นที่ 4 — ผู้ดูแลระบบคนแรก แล้วออกรหัสให้คนอื่น (5 นาที)

ไม่มีใครสมัครบัญชีเจ้าหน้าที่เองได้ ทุกบทบาทเกิดจากรหัสเปิดใช้งานที่ผู้ดูแลระบบออกให้

1. รัน `03_seed_staff.sql` ใน SQL Editor — จะได้รหัสเปิดใช้งานของชื่อผู้ใช้ `admin` **แสดงครั้งเดียว** (ฐานข้อมูลเก็บแค่แฮช)
2. เปิดหน้า login ของคอนโซล กรอก `admin` + รหัสนั้น → ระบบสร้างบัญชีให้ แล้ว**บังคับตั้งรหัสผ่านของตัวเอง**ทันที
3. เข้าเมนู **จัดการผู้ใช้** → ออกรหัสให้เจ้าหน้าที่แต่ละคน โดยเลือกชื่อผู้ใช้และบทบาทไว้ล่วงหน้า (Care Manager · เภสัชกร · นักกายภาพ · แพทย์ · พยาบาล · เจ้าหน้าที่บริษัทประกัน)
4. เจ้าตัวเข้าครั้งแรกด้วยชื่อผู้ใช้ + รหัสนั้น แล้วตั้งรหัสผ่านของตนเอง

> บทบาทมาจากรหัสที่ผู้ดูแลระบบออก ไม่ได้มาจากสิ่งที่ผู้สมัครเลือก · trigger `guard_role_change`
> กันการเลื่อนบทบาทตัวเองไว้ที่ฐานข้อมูล · รหัสหนึ่งใบใช้ได้ครั้งเดียว มีวันหมดอายุ และยกเลิกได้
> · ผู้ดูแลระบบไม่มีทางรู้รหัสผ่านของใคร รวมทั้งของตัวเองที่ระบบไม่เคยเห็น

## โครงสร้างข้อมูล

| ตาราง | เก็บอะไร |
|---|---|
| `profiles` | รหัสแฝงชื่อ ปีเกิด เพศ บทบาท — **ไม่เก็บเลขบัตรประชาชน ไม่เก็บที่อยู่** |
| `consents` | ความยินยอมแยกตามวัตถุประสงค์ ถอนได้ทีละอัน พร้อมขอบเขต (scope) |
| `assessments` | ผลประเมิน — **ตัวเลขล้วน ไม่มีคอลัมน์ใดเก็บภาพหรือวิดีโอ** |
| `risk_signals` | ผลเอนจินกฎ R1–R7 พร้อมเหตุผลรายข้อ |
| `referrals` | คิวเคสส่งต่อ — ต้องมีมนุษย์อนุมัติ |
| `audit_logs` | ร่องรอยทุกการกระทำ — **แก้ไม่ได้ ลบไม่ได้ แม้แต่ admin** |

## สิทธิ์เข้าถึงข้อมูล (บังคับในระดับฐานข้อมูล)

| | ผู้ใช้ | Care Manager | บริษัทประกัน | Admin |
|---|---|---|---|---|
| ข้อมูลตัวเอง | ✅ | — | — | ✅ |
| ข้อมูลผู้ใช้อื่น | ❌ | ✅ อ่าน | ❌ | ✅ |
| ตัดสินเคสส่งต่อ | ❌ | ✅ | ❌ | ✅ |
| พอร์ตความเสี่ยง | ❌ | ✅ | ✅ ผ่าน view เท่านั้น | ✅ |
| เห็นชื่อ/เบอร์โทร | ตัวเอง | ✅ (ต้องไปเยี่ยมบ้าน) | ❌ **ไม่มีทางเห็น** | ✅ |

**บริษัทประกันเข้าถึงข้อมูลได้ทางเดียวคือ view `insurer_portfolio`** ซึ่งมีแต่รหัสแฝงชื่อ
ช่วงอายุ เพศ และระดับสัญญาณ — บังคับที่ฐานข้อมูล ไม่ใช่แค่ซ่อนใน UI

## หลักการที่ schema บังคับใช้จริง

1. **ไม่มีที่เก็บภาพ** — ไม่มีคอลัมน์ไหนรับภาพหรือวิดีโอได้เลย
2. **AI ไม่มีสิทธิ์อนุมัติเคส** — trigger `guard_referral_decision` บังคับว่าผู้ตัดสิน
   ต้องเป็นบัญชีที่มีบทบาท `care_manager` หรือ `admin`
3. **Audit log แก้ไม่ได้** — ไม่มี policy สำหรับ UPDATE/DELETE
4. **ถอนความยินยอมมีผลทันที** — ถอน `share_pool` แล้วหลุดจากแดชบอร์ดทุกที่
5. **แยก self-reported ออกจาก verified** — คอลัมน์ `falls_source` / `meds_source` /
   `adl_source` เริ่มต้นเป็น `self_reported` เสมอ เปลี่ยนเป็น `verified_medical_record`
   ได้เฉพาะเมื่อมีความยินยอม `medical_record_check` และผ่านการตรวจสอบกับสถานพยาบาล

## ยังไม่ได้ทำ (ประกาศไว้อย่างเปิดเผย)

- **OTP ทาง SMS** — ปัจจุบันใช้เบอร์โทร + PIN เพราะการส่ง SMS ต้องมีผู้ให้บริการ
  ที่ผ่านการยืนยันตัวตนธุรกิจ โครงสร้างรองรับการสลับเป็น OTP โดยไม่ต้องแก้ schema
- **Data residency ในไทย** — ปัจจุบันอยู่สิงคโปร์
- **Penetration test / ISO 27001 / SOC 2** — ยังไม่ได้ทำ
- **การตรวจสอบเวชระเบียนจริง** — schema รองรับแล้ว แต่ยังไม่มี flow เชื่อมกับสถานพยาบาล
